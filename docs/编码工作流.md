# 编码工作流

整套流程靠 `git wf` 配合对话里的 AI 技能跑通：

**建 worktree → 写测试代码 → 完成代码 → 加载 `code-review` 与 `go-deslop` 技能 → 代码审查（调用技能）→ 提交代码并推送（含 lints 门禁）→ 提 PR**

AI 走到提 PR 为止；PR 由用户 review 后在网页合并，再用 `git wf clean` 清理。首次使用前在 `wf-plugin/` 跑一次 `bash install.sh`，它会检查并装齐 `git`、`python`、`gh`、`go`、`golangci-lint`、`lizard`，再把 `git-wf` 放进 PATH。

## 流程总览

| 步骤 | 执行方式 | 关键动作与门禁 |
|---|---|---|
| 1. 建 worktree | `git wf worktree <slug>` | 先看 `git wf status --all`；按规范建分支并独立开目录 |
| 2. 写测试代码 | 人工/AI | 在 worktree 内先写单测或可验收用例，明确预期行为 |
| 3. 完成代码 | 人工/AI | 实现功能并跑通 `go test`；程序能跑的就真跑一遍验证 |
| 4. 加载技能 | 对话里加载 | 常规加载 `go-deslop`、`code-review`、`de-ai-ify` 三个技能 |
| 5. 代码审查 | 调用技能 | 先 `go-deslop` 去冗余，再 `code-review` 深审；有问题在对话里修复并重测 |
| 6. 提交与推送 | `git commit` + `git wf push` | 按行为拆小提交；推送前先汇报；`push` 跑四项检查：gofmt/vet 未过硬拦，golangci/lizard 未过确认 `[Y/n]` |
| 7. 提 PR | `git wf pr` | 目标 `master`；`--close`/`--reopen` 关闭或重开 PR，`--edit` 改标题、描述、标签、评审人 |
| 8. 合并与清理 | 网页合并 + `git wf clean` | 用户手动合并；合并后执行 `git wf clean ../UESTC-Backup-<slug>` |

## 各步细则

### 1. 建 worktree

主工作区固定在 `master` 且保持干净，只用来查看和合并。每个任务或 AI 会话独立开一个 worktree：

```bash
git wf status --all                                # 查看现有 worktree、分支和关联 PR
git wf worktree <slug> [-t feat] [-i <issue号>] [-d <目录>]   # 建 worktree，默认在 ../UESTC-Backup-<slug>
git wf worktree <slug> --from <已有分支>           # 直接检出已有分支（不新建分支）
```

- 目标分支已经在 `git wf status --all` 里出现就换个名字，不要去抢。
- 若主工作区有未提交改动，`git wf worktree` 会列出提示；先弄清改动归属，不要执行 `checkout`、`pull` 或 `stash`。
- 确认当前没有并行会话或 worktree 时，单人临时小改动才可用 `git wf branch <slug>` 在当前工作区切分支；不涉及代码隔离的文档小修改也可直接处理。

#### 分支命名

`git wf` 按下面格式自动生成分支名（可用 `-n` 预览）：

```
<type>/<用户名>/<slug>[-<issue号>]/<YYYYMMDD>
例: feat/whalefall/archive-crc/20261125      没有对应 issue
    feat/whalefall/archive-crc-12/20261125   对应 issue #12
```

- `type`：`feat | fix | chore | docs | refactor | test | dev`，默认 `feat`（其他值告警后仍可用）
- `用户名`：取 `git config user.name` 小写并去掉空格
- `slug`：小写字母、数字和连字符（空格、下划线自动转连字符），有对应 issue 时接 `-<issue号>`

### 2. 写测试代码

切进新建的 worktree 目录后，先写测试代码再写实现：

- 先把正常路径、边界条件和异常输入写成 `*_test.go` 用例（刚写完时编译或运行失败属正常）。
- 测试使用标准库 `testing`，不引第三方断言库；失败信息用 `Func(%v) = %v, want %v` 格式。

### 3. 完成代码

围绕测试实现功能，确认测试全部通过：

- 跑测试：`client/` 下执行 `go test ./... -count=1`（按需加 `-cover` 或 `-race`）。
- **自己跑一遍**：测试只证明写过的用例。能直接运行的程序就按真实用法走一遍，比如打包样例目录再还原；必须人手点界面时，把操作步骤和预期结果列清楚让用户测。
- 开发过程中随时用 `git wf status`、`git wf diff`、`git wf review` 看变更统计和异常提示（疑似调试打印、`TODO`/`FIXME`、行尾混入 CRLF+LF、diff 行数超限等）。

### 4. 加载技能

自测通过后、提交前，在对话里显式加载下面三个项目技能：

- `.agents/skills/go-deslop/SKILL.md`
- `.agents/skills/code-review/SKILL.md`
- `.agents/skills/de-ai-ify/SKILL.md`

提交信息、PR 说明和大段注释一定会过 `de-ai-ify`，常规加载避免遗漏。

### 5. 代码审查（调用技能）

按顺序过一遍：

1. **`go-deslop`**：对照本分支相对 master 的全部变更（`git wf diff`，含工作区未提交改动）做瘦身 pass，清理过度设计、不可能场景的防御、复述代码的废话注释和未请求的功能
2. **`code-review`**：审查需求一致性、并发安全、安全性、潜在 Bug、资源管理和 Go 编码规范；禁止写审查报告文件，输出问题即可。
3. **修复闭环**：有 Critical/Major 问题就改完重跑前两个操作

### 6. 提交代码与推送（含 lints 门禁）

#### 提交代码

先用 `git wf diff` 和 `git wf review` 看一遍变更，再按“一个能独立验收的行为”拆提交：

- 单次提交增删合计控制在 300 行以内；纯移动或重命名的提交标题写明“只移动”，review 时用 `git wf diff`（自带 `-M --color-moved`）核对。
- 提交信息用中文 Conventional Commits：

```
<type>: <中文说明>
例: feat: 归档的打包、读取与 CRC 校验
```

- `type` 与分支名一致（`feat | fix | chore | docs | refactor | test | dev`），说明只写改了什么、保证了什么。

#### 推送前汇报

提交完成、推送之前，用一段话向用户汇报本阶段做了什么（思路、功能）以及保证了什么（如不可读文件跳过、失败不留半截文件、取消能退干净），过一遍 `de-ai-ify` 再推送。

#### 跑 lints 与推送

开发过程中按需执行 `git wf check`，单独跑四项检查。正式推送使用 `git wf push`，推送前自动跑一遍同样的检查。

四项检查：

1. `gofmt`：校验 `client/` 下所有 Go 文件格式（硬性）
2. `go vet ./...`：在 `client/` 下跑静态检查（硬性）。
3. `golangci-lint run`：使用仓库根目录 `.golangci.yml`，包含标准 linter、`gosec`、`funlen`（函数 ≤ 100 行）以及 `revive` 的 `argument-limit`（参数 ≤ 5）、`max-control-nesting`（嵌套 ≤ 4）、`file-length-limit`（实现文件 ≤ 400 行）等规则（警告级）。规模上限是审查阈值，不是要求机械拆分的硬性目标。超限时优先判断是否存在独立职责、重复逻辑或复杂度过高。只有拆分能改善可读性和维护性时才拆分，不为满足行数限制制造无意义的辅助函数。确有合理理由时，可以保留超限实现并说明原因：单点豁免在对应位置加 `//nolint:<规则名> // 原因`，整体放行走推送时的确认。
4. `lizard -C 15 -l go`：检查圈复杂度（警告级；默认阈值 15，`check` 和 `push` 都可用 `--ccn <数>` 调整）。

gofmt 和 go vet 是硬性检查，未过直接拒绝推送，没有跳过通道；golangci-lint 和 lizard 是警告级，未全过时列出失败项和未提交文件数，交互确认 `[Y/n]`（回车默认推送，答 n 取消），`--yes` 跳过询问。未全过时优先回第 5 步修复；确要保留超限实现，按上面的方式豁免并在汇报里说明。任何时候不要绕过插件直接 `git push` 躲开检查。

在 `master` 上执行 `push` 或 `pr` 会被拒绝。

### 7. 提 PR

汇报完成、推送成功后创建 PR（默认目标 `master`）：

```bash
git wf pr -t "<标题>" [-d "<描述>" | -F <描述文件>] [--label ...] [--reviewer ...] [--draft]
```

- 标题默认取分支名里的 `slug`（去掉末尾 issue 号）；需要修改已建 PR 的标题、描述、标签或评审人时用 `git wf pr --edit`（`--label` 和 `--reviewer` 支持 `+增 -删`）；关闭或重开 PR 用 `--close` / `--reopen`（隐含 `--edit`，不带 `-n` 时定位当前分支的 PR）。PR 描述同样过一遍 `de-ai-ify`。
- PR 合并由用户在 GitHub 网页上完成。AI 不得执行 `gh pr merge`，也不要代为点网页。

#### 撤回

推错分支或方向不对时，撤回远端分支（本地保留）：

```bash
git wf unpush [--yes]
```

- 分支有开放 PR 时会拒绝，先 `git wf pr --close` 再撤回。
- 确认提示 `[y/N]` 默认不删，`--yes` 跳过确认。

### 8. 合并后清理

用户在网页合并 PR 后，从主工作区或其他目录执行（脚本自己会退出目标目录，但执行它的 shell 所在目录被删后，后续命令会报错）：

```bash
git wf clean ../UESTC-Backup-<slug>
```

`clean` 会校验目录无未提交改动，随后移除 worktree、在主工作区 `master` 上 `git pull --ff-only`，并尝试删除已合并的本地分支。worktree 里不要留未跟踪文件——过程文档一律放主工作区 `docs/`，否则 `clean` 的脏检查会拒绝清理。

## 代码约定与规模上限

### Go 注释约定

- 函数注释一行简短中文说清；导出函数保留一行 Godoc，以函数名开头，如 `// OpenArchive 打开并校验归档头`。
- 每个 Go 文件第一行直接写 `package xxx`，不加包注释（`//go:build` 构建标签等指令行除外，它们必须在 `package` 之上）。
- 注释行末不加标点（`。`、`；`、`.`、`;` 都不要）。
- 只写后来的人大概率不知道的事：约束、意图、踩过的坑；代码本身能看出来的别写。

### 规模上限与检查方式

| 项 | 上限 | 超了怎么改 | 检查方式 |
|---|---|---|---|
| 函数参数 | 5 个（含 ctx） | 可选参数收进最后的 `XxxOptions`；ctx 不进结构体 | `golangci-lint`（`revive:argument-limit`） |
| 函数嵌套 | 4 层 | 卫语句提前 return | `golangci-lint`（`revive:max-control-nesting`） |
| 实现函数 | 100 行 | 按“准备输入 / 干活 / 收尾”拆开，函数名说明职责 | `golangci-lint`（`funlen`） |
| 实现文件 | 400 行 | 按职责拆，文件名说明职责；别拆成 `types.go`、`utils.go` | `golangci-lint`（`revive:file-length-limit`）+ `git wf review` |
| 测试文件 | 500 行 | 跟着被测文件走，共享辅助放 `helpers_test.go` | `git wf review`（新文件）+ `code-review` |
| 测试函数 | 100 行 | 用例数据抽成 `xxxBytes()`、`xxxCases()` 之类辅助 | `code-review` |
| 一次提交 | 300 行（增 + 删） | 按独立可验收行为拆；纯移动在标题写“只移动”，如 `refactor: 只移动归档模块到 internal/archive` | `git wf review` |

测试文件已在 `.golangci.yml` 豁免 `funlen`、`file-length-limit` 和 `argument-limit`，测试函数与文件的行数上限由 `git wf review` 和 `code-review` 把关。

以上检查只覆盖 `client/`；改动 `wf-plugin/` 本身时，验证方式是 `python -m py_compile` 加在真实仓库里跑一遍对应命令。

## 文字与文档

- 凡是别人能看到的文字，超过两句话先过一遍 `de-ai-ify`：注释、提交信息、PR 标题和说明、执行计划、需求/设计/测试文档都算。
- `docs/` 下的工作流与过程文档默认留在工作区，用户明确说“提交某份文档”才 `git add`。

### 对外文字的三条规则

PR 说明、提交信息、大段注释，以及其他给别人看的文字，必须使用 `de-ai-ify` 过一遍。遵循下面的要求：

1. 不写看代码就能明白的东西。函数签名、文件位置、明显的实现细节都算废话。
2. 不写自己编码时做了什么。测试在哪跑、报告留在哪、这是第几步，这些过程说明不进 PR、commit 和注释。
3. 只简要写代码做了什么、保证了什么，句子越短越好，不留 AI 味。

## 多 session

### 协同约定

- 不同会话不共用同一个 worktree；一条分支只在一个 worktree 里检出。
- 不在其他会话的 worktree 里执行 `checkout`、`pull`、`commit` 等写操作；确实要动别人的目录，先在对话里确认。

### 排障

主工作区分支错乱或出现悬空改动时，先看两条命令再动手：

```bash
git wf status --all         # 所有 worktree 各自在哪条分支、有几个脏文件、PR 状态
git reflog -15 --date=iso   # 主工作区 HEAD 的切换记录
```

## 依赖与降级

- **工具链依赖**：由 `wf-plugin/install.sh` 统一检查与辅助安装；插件更新后重跑一次 `bash install.sh` 即可覆盖安装。装完会检查 gh 是否已登录，未登录只警告不阻断。
- **`gh` CLI 未登录**：`git wf pr` 会打印手动建 PR 的链接与建议标题，不中断流程；登录一次（`gh auth login`）即可自动创建和编辑 PR。
- **GitHub 网络不稳**：`push`/`pr` 失败时稍后重试；Go 工具链拉模块加 `GOPROXY=https://goproxy.cn,direct` 前缀。

## `git wf` 命令速查

| 命令 | 用途 |
|---|---|
| `git wf worktree <slug> [-t feat] [-i 12] [-b master] [-d 目录] [--from 分支]` | 开 worktree + 开工检查；`--from` 直接检出已有分支 |
| `git wf branch <slug> [-t feat] [-i 12] [-b master] [-n]` | 当前工作区自动命名建分支 |
| `git wf status [--all]` | 当前工作区和分支状态；`--all` 看全部 worktree |
| `git wf diff [基线] [--stat] [--word-diff] [路径...]` | 面向 review 的变更展示（`-M --color-moved`） |
| `git wf review [基线]` | 变更体检：规模、分布、调试残留、行尾混入 |
| `git wf check [--ccn 15]` | 跑 `gofmt`、`go vet`、`golangci-lint`、`lizard` 四项门禁 |
| `git wf push [--ccn 15] [--yes]` | 跑四项检查后推送：gofmt/vet 未过硬拦，golangci/lizard 未过确认 `[Y/n]`，`--yes` 跳过 |
| `git wf unpush [--yes]` | 撤回远端分支（本地保留）；有开放 PR 时拒绝 |
| `git wf pr [-t 标题] [-d 描述 \| -F 文件] [--label] [--reviewer] [--draft] [--edit] [--close] [--reopen]` | 建 PR；`--edit` 修改已有 PR，`--close`/`--reopen` 隐含 `--edit` |
| `git wf clean <worktree目录>` | 合并后删 worktree、主工作区 `pull`、删本地分支 |
