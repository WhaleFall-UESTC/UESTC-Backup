# 第 1 章: 基本原则

## Core Idea
可读性四原则按重要性排列：**逻辑清晰 > 简单 > 简洁 > 可维护性**，外加一致性约束。所有后续章节的规则都是这四原则的具体化。

## Frameworks Introduced
- **逻辑清晰**: 通过三个手段实现——准确的命名、有用的注释、合理的代码组织结构。
  - When to use: 写任何代码时的首要自检标准——读者能否不问作者就看懂。
- **简单（最少依赖原则）**: 用最简单的代码实现目标，逻辑复杂度最低、性能最高。依赖选型按优先级：
  1. 直接用基础数据结构（管道、切片、映射等）
  2. 不满足再用标准库工具（如 net/http）
  3. 确认社区没有可用库之后，才自己编写工具库
  - 判断信号: 功能很简单但代码逻辑异常复杂 = 陷入了不必要的复杂性。
- **简洁**: 不包含与功能无关或不必要的代码。五大危害场景按危害排序：重复代码（危害最大）、多余代码、晦涩难懂的命名、过度抽象、多余空行。
- **可维护性**: 上线后会被多次修改。特征：组织结构化的 API、关注要解决的功能问题而非结构本身、避免耦合、不为未使用的功能写代码、测试用例完备、不在易忽略处隐藏细节。
- **一致性**: 包内一致性最重要；同一问题在一个包里只用一种解法，同一概念只有一个名称。**一致性与旧代码习惯冲突时，以代码规范为准**，旧代码逐步迁移。

## Anti-patterns
- **错误处理反着写**: 用 `err == nil` 作为主路径判断——应遵循 Go 惯用法 `err != nil`。
- **隐藏关键细节**: `if user, err = db.UserByID(...)` 中 `=` 与 `:=` 之差会改变整行语义，极易改错。
- **复杂布尔表达式压缩成一行**: `leap := (year%4 == 0) && (!(year%100 == 0) || (year%400 == 0))` 中的 `!` 极易漏看。应拆成命名布尔变量再组合。
- **过度分包**: 简单功能拆成 model/api/service/repository/utils 五层目录。Good 是平铺：`user/` 下直接放 `user.go`、`api.go`、`service.go` 等。
- **同一概念多种实现风格**: 计算 `Area()` 用成员函数，`Perimeter()` 却写成包级函数 `CalculatePerimeter(rect)`。

## Code Examples
```go
// Good: 拆解复杂条件，命名每个子条件
var (
    leap4   = year%4 == 0
    leap100 = year%100 == 0
    leap400 = year%400 == 0
)
leap := leap4 && (!leap100 || leap400)

// Good: 遵循 Go 习惯用法
if err := doSomething(); err != nil {
    // ...
}
```
- **What it demonstrates**: 用命名变量降低布尔逻辑理解难度；错误处理走惯用路径。

## Key Takeaways
1. 四原则有优先级：逻辑清晰是第一位，简洁性中重复代码危害最大。
2. 依赖顺序：基础结构体 → 标准库 → 第三方/自研，逐级降级。
3. 复杂条件拆成命名布尔变量；关键但易漏的符号（`!`、`=` vs `:=`）不要埋在长表达式里。
4. 包结构按需而定，简单功能不过度分层。
5. 一致性冲突时以代码规范为准，旧代码向规范迁移。
